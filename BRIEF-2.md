# Brief: Catch-up and agent-assisted collision resolution

## Context

The v1 review UI shipped with `Has collisions` as a surfaced state but no resolution surface — collisions had to be resolved in the terminal. This brief adds the catch-up flow and the collision resolution flow, going directly to the agent-assisted version rather than shipping a manual-only intermediate.

The premise: when a task's parent moves, the user shouldn't have to leave the GUI to bring the task in line, and shouldn't have to do conflict resolution by hand. The same agent pipeline that produced the proposal can produce a resolution proposal, reviewed the same way.

## Principle

A proposal is reviewed against the parent it was authored against. The moment the parent moves, that approval is stale — the changes need to be re-evaluated. Catch-up is the verb for "bring the proposal in line with the new parent." Collision is the state when catch-up needs help. The user's role throughout is review-and-approve, never manual resolution (unless they choose to drop to the terminal as an escape hatch).

## Trust model

This is the part that has to be right. The whole flow only works if users trust that what they review is what they land.

- **Detection of needed catch-up is automatic.** Background dry-runs against the current parent run continuously; task state reflects reality.
- **Performing catch-up requires explicit user action.** The system never silently rewrites a task's revisions. A `Catch up` click is required.
- **After any catch-up (clean or resolved), the auditor pipeline re-runs.** The previous verdict was given against the old parent and does not carry over.
- **The auditor's role gets heavier in this flow.** With agent-assisted resolution, the human doesn't see the resolution work happen — they only see the resulting proposal. The auditor is the only automated gate between "agent modified your files during rebase" and "you landed it." Treat auditor verdict for resolution proposals as a hard requirement, not an advisory.

## Vocabulary additions

| Term | Meaning |
|---|---|
| **Catch up** | Bring a task in line with the current parent |
| **Resolution proposal** | A proposal whose purpose is to resolve collisions during catch-up, generated by the agent against an auto-derived spec |
| **Has collisions** | State when catch-up produced collisions (already in vocabulary, formalised here) |

Existing terms used: `Proposal`, `Land`, `Under review`, `Approved`, `Ready to land`, `Needs catch-up`, `Catching up`.

## Detection: when a task enters `Needs catch-up`

A background process watches each workspace's parent ref. When it moves, every approved-and-not-yet-landed task in that workspace gets a dry-run rebase against the new parent. The result updates `tasks.catch_up_state`:

- `clean` — rebase would succeed without conflicts; task stays in `Ready to land` but is marked stale
- `dirty` — rebase would succeed but produces a different diff than what was reviewed; task transitions to `Needs catch-up`
- `colliding` — rebase produces conflicts; task transitions to `Needs catch-up` with a sub-flag indicating collisions will occur

The distinction between `clean` and `dirty`: a clean rebase changes nothing about the proposal's content (the new parent and the proposal don't touch overlapping files). A dirty rebase succeeds mechanically but the resulting diff has changed because the parent's new state shifts what the proposal's changes mean. Both require auditor re-run; the difference is only relevant for messaging the user.

For v1 of this brief, treat `clean` and `dirty` identically (both trigger `Needs catch-up`). The distinction is data-modelled now so future versions can opt to auto-catch-up the truly-clean case if we decide that's safe.

## UI: task in `Needs catch-up`

Task page header changes:

- State pill: `Needs catch-up` (amber, matching pipeline warning colour)
- Primary action button: `Catch up` replaces `Land`. `Land` is not rendered.
- Banner above the auditor verdict:
  - Text: "Parent has moved. Catch up to re-evaluate this proposal against current state."
  - Sub-text (muted, smaller): "N changes from M tasks landed since this proposal was approved." Where N and M are derived from the parent's history since `tasks.merge_base_sha`.
  - Optional: small expandable list of the intervening landed tasks (title + link).
- The proposal view remains visible but with a muted banner: "These changes are shown against the old parent. Catch up to see them against current state."

## Catch up: clean path

User clicks `Catch up`. System attempts rebase onto current parent.

- **Optimistic UI**: state immediately becomes `Catching up`, button replaced with a progress indicator.
- **On success without collisions**: 
  - State transitions to `Under review`
  - Auditor pipeline re-runs automatically (same pipeline that originally evaluated the proposal)
  - Banner replaced with: "Caught up to current parent. Re-running auditor."
  - When auditor completes, state transitions per its verdict (back to `Approved` → `Ready to land`, or `Under review` if rejected — same as initial flow)

The user can watch the pipeline re-run in the right rail, same as the original review. No new surfaces needed.

## Catch up: collision path

If the rebase produces collisions, system transitions task to `Has collisions` and opens the **collisions view**, replacing the proposal view in the task page body.

### Collisions view structure

Header:
- State pill: `Has collisions` (red)
- Primary action: `Ask agent to resolve` (the default agent-assisted path)
- Secondary action: `Resolve in terminal` (escape hatch)
- Tertiary action: `Cancel catch-up` (returns task to `Needs catch-up`, restores pre-catch-up state, useful if user realises they want to delete the task instead)

Body — for each colliding file:
- File path with collision count
- Each collision shown as a three-column view:
  - **Current parent**: what's now on the parent at this location, with an attribution badge naming the landed task that introduced this version ("From: `Restructure CountryCard`, landed 2h ago")
  - **This proposal**: what the agent produced for this location
  - **Common ancestor**: the base version (smaller, muted, for reference)
- Read-only in v1 of this brief. No inline editing. Resolution happens either via agent (primary path) or terminal (escape hatch).

### "Ask agent to resolve" — the primary resolution path

This is the killer feature. User clicks `Ask agent to resolve`.

**System generates a resolution brief automatically.** The briefing phase already exists and handles dependency-aware task generation with acceptance criteria — feed it the right inputs and let it do its work. The inputs for a resolution brief are:

- The original task's spec and acceptance criteria
- The set of colliding files and their three-way contents
- The diff of the intervening landed tasks (what's changed on the parent)
- A standing instruction template specific to resolution: "produce a resolution that preserves the original acceptance criteria while integrating cleanly with the current parent. Where the parent has introduced changes that conflict with the original proposal's approach, prefer the parent's approach unless it breaks the original acceptance criteria."

The briefing phase produces a resolution task, which spawns a resolution proposal — same lifecycle as any other task. The user is shown:

- A new sub-view: "Resolution in progress" with the standard pipeline display (implementer → gate → auditor)
- They can watch it run, view artifacts, etc., same as a normal task

**When the resolution proposal completes auditor review:**

- If auditor approves: state of the *parent task* transitions to `Under review` for the resolution. The user sees a normal proposal view showing the resolution's changes (which include both the agent's original work and the resolution edits, on top of the new parent). They review and either approve-and-land or pass back with notes.
- If auditor rejects the resolution: state stays at `Has collisions`, the failed resolution is shown in the audit trail, user can re-ask the agent (potentially with notes) or drop to the terminal.

**Key data model point**: a resolution is a proposal *of* the parent task, not a separate task. The task's `proposals` collection now has at least two entries — the original implementation proposal, and the resolution proposal. Both are visible in the task's history. This is the multi-proposal data model already on the roadmap; this brief makes it concrete.

### "Resolve in terminal" — the escape hatch

User clicks `Resolve in terminal`. System opens a terminal pinned to the task with the rebase already in progress (the dry-run becomes the real run). Standard Git resolution from here.

When the rebase completes (detected via worktree state watching, which already exists for terminal lifecycle):
- Successful rebase → state transitions to `Under review`, auditor re-runs
- Aborted rebase → state returns to `Needs catch-up`

No GUI for the resolution itself — that's the price of the escape hatch, and we accept it because the agent-assisted path is meant to be the path users actually take.

## UI: resolution proposal review

When a resolution proposal reaches `Under review` and then `Approved`, the user sees the parent task's page with:

- State pill: `Under review` (during) or `Ready to land` (after approval)
- A small banner at the top: "Reviewing resolution proposal. The original proposal had collisions with parent that have been resolved."
- The proposal view shows the *resolution's* changes (the full set of changes against new parent, which is what would actually land)
- A toggle: "Show original proposal" — for users who want to compare what the agent originally produced against the resolved version. Default off.
- Author badges work normally; the resolution proposal's hunks will mostly carry the resolving agent's badge, with some hunks unchanged from the original proposal carrying their original badges.

The `Land` button then operates on the resolution proposal as the thing being landed. Squash commit message includes both the original task's acceptance and the fact that a resolution was applied:

```
{task title}

{auditor verdict summary}

Resolved collisions during catch-up with parent. Resolution against {intervening task titles}.

Co-authored-by: {original proposal authors}
Co-authored-by: {resolution proposal authors}
```

## Data model additions

- `tasks.catch_up_state` — enum: `none | clean | dirty | colliding`, with timestamp of last check
- `tasks.proposals` — collection of proposals associated with the task. Each proposal has: `id`, `kind` (`implementation | resolution`), `auditor_verdict`, `created_at`, `superseded_by`, and a pointer to its revision range.
- `tasks.active_proposal_id` — which proposal is currently the canonical one (the one that would land if `Land` were clicked)
- `proposals.parent_collisions` — for resolution proposals, the set of collisions they were spawned to resolve, kept for audit purposes
- New audit event types: `CatchUpStarted`, `CatchUpSucceeded`, `CollisionsDetected`, `ResolutionRequested`, `ResolutionLanded`

## Background processing

A new worker watches each workspace's parent branch ref for changes. On change:

1. For every approved-and-unlanded task in the workspace, enqueue a dry-run rebase check
2. Dry-run runs in an ephemeral worktree clone to avoid touching the task's actual files
3. Update `catch_up_state` based on result
4. Emit events for any state transitions

Polling interval: 30s on the parent ref is fine for v1; can be event-driven later if performance demands.

## Non-goals for this iteration

- **Auto-catch-up of `clean` cases.** Even when a rebase would change nothing, we require explicit user action and auditor re-run. Revisit only with strong evidence users find this annoying.
- **Inline editing in the collisions view.** Three-way view is read-only. Editing happens via agent or terminal.
- **Multiple parallel resolution attempts.** Only one resolution proposal active at a time; passing back with notes supersedes rather than spawning siblings.
- **Surfacing `clean | dirty` distinction in UI.** Both shown identically as `Needs catch-up` for now.
- **Cross-workspace catch-up.** This brief assumes the parent is within the same workspace. Cross-workspace dependencies are out of scope.

## Open questions for the implementer

1. **Resolution prompt template ownership.** The "preserve acceptance criteria, prefer parent approach when in conflict" instruction is the most important sentence in this whole flow. Where does it live, who edits it, how is it tuned over time? Recommendation: in workspace settings, with a sensible default, surfaced as an editable template so power users can tune.
2. **Resolution failure loop.** If the agent's first resolution proposal is rejected by the auditor, and the user re-asks, does the re-ask receive the auditor's rejection notes? Recommendation: yes, fed in as additional context to the briefing phase. This makes the second attempt smarter than the first.
3. **What if the parent moves *during* resolution?** A resolution proposal is in flight, parent moves again, the resolution is now itself stale. Recommendation: abort the resolution, return to `Has collisions` with fresh collision data against newest parent, surface a note explaining what happened. Don't try to be clever.
4. **Performance: ephemeral worktree clones for dry-runs.** At 30s polling across many tasks, this could get expensive. Confirm approach — git's own native dry-run capabilities (`git merge-tree`) may be sufficient and cheaper than full clones.

## Acceptance criteria

- Background worker detects parent ref changes and updates `catch_up_state` for approved tasks within 60s.
- Task in `Needs catch-up` shows the amber pill, `Catch up` button replaces `Land`, banner explains the situation with accurate counts.
- Clicking `Catch up` on a non-colliding task performs the rebase, transitions to `Under review`, re-runs the auditor pipeline, and lands cleanly via the existing land flow.
- Clicking `Catch up` on a colliding task transitions to `Has collisions` and opens the collisions view with three-way display and parent attribution.
- Clicking `Ask agent to resolve` generates a resolution brief, spawns a resolution proposal via the briefing pipeline, and runs it through the standard implementer → auditor flow.
- Approved resolutions are presented as the proposal-under-review for the parent task; the user can review, compare against the original proposal via toggle, and land.
- Landing a resolved task produces a squash commit with the resolution-aware message format and co-authorship trailers for both original and resolution authors.
- The terminal escape hatch works: dropping to terminal during collisions opens a rebase-in-progress shell; completing or aborting the rebase transitions the task state appropriately.
- All vocabulary remains consistent with the existing domain language (no `merge`, `rebase`, `conflict`, `HEAD` appearing in user-facing strings outside the terminal).
